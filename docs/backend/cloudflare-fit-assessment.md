# Workers Free + D1 + Cron是否满足GainTrace

2026-11-19。范围：现有代码/公开限制/合成账本本地容量测算。未创建Cloudflare资源、同步真实账本或进行云端部署测试。

## 判断

适合个人或少量用户的第一版后台，有机会在免费额度内完成交易同步、服务端每日盈亏记录、滚动一年历史和备份导出。不能原样搬运当前前端实现，也不能保证支持现有导入上限10万笔交易的任意账本、任意标的数量或任意用户规模。

上线前仍须在实际Workers上验证CPU、D1开销、行情出网与国内手机访问；本地Node测算不足以证明满足云端10msCPU限额。

## 需求逐项评估

| 需求 | 适配程度 | 必须做的设计 |
|---|---|---|
| 交易新增、编辑、删除和同步 | 可实现 | 独立账户授权、按用户索引、账本版本、冲突处理；操作确认云端已保存后才把后台视为知晓该交易 |
| App关闭时每天生成账户盈亏 | 可实现 | 已录入账本或必要持仓状态需同步云端；Cron读取账本和已确认价格计算。只后台采行情、不开通账本同步时，账户盈亏仍只能打开后计算 |
| 沪港美收盘与历史汇率 | 平台支持外部HTTPS访问，源可用性未验证 | 当前供应商接口只从本机探测过；需验证Workers出网、接口数据质量/限制、市场交易日与夏令时规则 |
| 当前持仓和今日暂估 | 可实现 | 继续实时估值，与已确认历史收盘记录分别存储；请求适度缓存 |
| 历史回填/账本回溯更正 | 可实现但不能整年一次处理 | 用可恢复游标分批读取/计算/提交；每批按实际CPU自适应，保存账本版本，重试幂等；暂估或数据不齐时不写确认点 |
| 滚动365天及清仓交易记录 | 个人规模容量足够 | 历史快照按日期清理，原始交易记录长期保留；旧交易结转已实现盈亏和持仓基线 |
| 隐私金额/百分比、排序等前端交互 | 可继续保留 | 共用同一份每日记录与历史买入分母，排序独立于交易账本 |
| 备份恢复 | 有平台恢复及导出能力 | D1 Free时间点恢复窗口7天，不能替代独立长期账本备份；保留完整JSON导出并测试迁移恢复 |

## 免费配额及容量

核查的官方限制：

- Workers每日100,000请求，单次HTTP与Cron CPU10ms；等待网络和数据库不计CPU。
- Free最多5个Cron触发器/账户，单次外部子请求50个，并发外连上限6个。按市场/日期调度一组批量任务，不按每只股票或每个用户单独创建Cron。
- D1总存储5GB、最多10库，但单库最高500MB；每日读500万行/写10万行。索引与表一起消耗存储，更新索引会增加写入量。
- D1单Worker调用50次查询；当前官方说明db.batch()对调用计数算一次，仍须控制CPU、单语句及批量大小。
- D1免费时间点恢复窗口7天。配额耗尽可导致请求/查询失败，不等于后台会自动完成任务，必须保留重试与补算状态。

合成1000笔交易、50标的：当前账本JSON约171KB，单个全持仓快照约5.46KB。用该快照大小乘365约1.99MB；实际构造365个历史快照约1.87MB。十个类似账户的快照原始载荷量级约20MB，尚需加交易表、索引、行情缓存、日志等，不能把原始载荷当完整数据库实际用量。对当前个人/少量用户，容量有充分余量。

行情应按标的和交易日共享，不为每个账户重复抓取。历史价格仅抓所需范围，避免每次任务重拉整年；相同账本版本下每日增量估值，历史修改才分批回算。SQL按用户/日期/标的建索引，避免每次全库扫描消耗每日读额度。

## 本地性能探针

脚本`cloudflare-capacity-probe.mjs`加载真实`parts/core.js`与`parts/pnl.js`，使用合成沪港美账本，没有读取个人持仓。

| 交易笔数/标的数 | 单日buildSnapshot CPU中位数 | 当前capture同步预处理 CPU中位数 | 预处理CPU P95 |
|---|---:|---:|---:|
| 100 / 10 | 0.050ms | 0.145ms | 0.299ms |
| 1000 / 50 | 0.367ms | 1.380ms | 3.436ms |
| 10000 / 100 | 3.008ms | 12.287ms | 15.599ms |
| 100000 / 200 | 33.422ms | 160.392ms | 169.793ms |

1000笔/50标的一次朴素重建365天：CPU中位数88.989ms，3次样本P95 110.768ms。三份公开历史响应合计154,050字节，本地JSON解析CPU中位数0.430ms。

含义：小账本的单日处理有实现空间；批量补算和大账本全量复制、排序、生成签名不适合单次10ms预算。后台应存计算基线/累计状态，读取增量，按独立调用切分回填，而非在同一个Worker里仅用await把长计算伪装成分批。CPU重型认证或其他处理中间件也要计入预算。

限制：以上是本机Node/VM进程CPU，包含运行时/GC影响，不包含云端授权、D1读取/写入、云端网络及实际调度。CPU数字不是Workers实测结果，也不保证任一具体用户数据会落在同等时间内。原始结果见`cloudflare-capacity-results.json`。

## 建议第一版形态

前端继续现有页面；Worker API处理账户与交易同步；D1保存交易、估值状态、历史行情、每日快照及任务状态；Cron定期选择已到收盘确认时点的工作，分小批执行、落游标、失败后补算。前台今日暂估和确认历史分开。

云端验证先用合成账本：1000笔/50标的与大账本边界场景，实际测HTTP与Cron CPU；从Worker获取沪港美及历史汇率；手机Wi-Fi/移动网络访问；测试关闭前端后任务仍写入记录；故障重试、漏日补算、版本冲突和备份恢复。证据通过后再迁真实数据。

最终建议：选为第一版候选。若实测CPU经分批/增量后仍频繁超限，选择Workers付费最低5美元/月或回到固定区域服务器；不承诺永远免费或现有10万笔账本导入能力全量后台执行仍免费。

依据：[Workers limits](https://developers.cloudflare.com/workers/platform/limits/)、[D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/)、[D1 limits](https://developers.cloudflare.com/d1/platform/limits/)、[Cron](https://developers.cloudflare.com/workers/configuration/cron-triggers/)。
